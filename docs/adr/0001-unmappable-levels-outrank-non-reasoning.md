# ADR-0001：端点公布的不认识档位，优先于「非推理」判定

## 状态

已采纳（2026-10-07）

## 背景

spec 的两条映射规则落在同一个输入上：

- 「端点明确公布能力、且不含任何可声明的正向等级 → **非推理**，判 `clear`」；
- 「有推理但过滤后没有任何可声明等级 → 判 `keep` 并报告（适配器拒绝空字典）」。

`supported_efforts: ["ultra"]` 同时满足这两句的字面条件：端点确实公布了能力，而过滤掉
适配器不认识的 `ultra` 之后，可声明的正向等级是空的。两种读法导出的行为相反——
`clear` 会把这个模型已有的等级声明写成非推理，`keep` 一个字都不写。

这不是文字游戏：`clear` 是**破坏性**的。端点新加一个档位名（例如 `ultra`）而插件不认得它时，
`clear` 会把用户已经声明好的 `low/high` 全删掉，理由只是"插件不认识新名字"。这正是
user story 28 要防的事——「端点公布了我适配器不认识的档位时被报告出来而不是被猜测」。
猜一个映射是猜，把不认识当成"没有"也是猜。

## 决定

**`capability.unknown` 非空时，判定不可能是 `clear`；这种 `keep` 的 `reason` 是
`unmappable`，与"端点什么都没说"的 `unknown` 分开。**

优先级是：

1. 端点没有这个模型 / 没有 `reasoning` 字段 → `keep`（`cloaked` / `unknown`）；
2. 过滤后**剩下的都是不认识的名字** → `keep` 并报告（`reason: unmappable` + `capability.unknown`）；
3. 过滤后为空、且**没有任何不认识的名字**（`supported_efforts` 为空或只有 `none`）→ `clear`；
4. 过滤后有可声明的等级 → `update` 或 `keep`（`in-sync`）；此时若同时存在不认识的名字，
   认识的照写、不认识的照报——写认识的那一半不是猜测。

只有第 3 条是「端点明确说这个模型不能推理」，因为端点在那种情况下**没有**说出任何插件
读不懂的东西。`supported_efforts` 为空、或只有 `none`（"关掉推理"的 wire 值），都是
「没有可声明的正向等级」的正面陈述。

## 后果

- 端点新增一个陌生档位名时，同步的结果是**报告**，不是静默删除等级；用户看到"端点公布了
  本适配器不认识的档位"后自己决定要不要手工映射。
- 插件在 `supported_efforts` 只有 `none` 的模型上会写 `reasoningEfforts: false`（见 ADR-0002），
  因为那才是端点说的话。
- 代价：如果端点真的把某模型改成非推理、同时又暂时留了一个陌生档位名，插件会先报不改；
  下一次端点清理干净后才会 `clear`。这个滞后是可接受的，反向的错误不可接受。
- `CONTEXT.md` 的**未知**只指"端点没有公布能力"，**不认识**另立一条：两者都会 `keep`，
  但读者要能分清是端点没说、还是插件读不懂。
