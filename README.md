# dsh-reasoning-sync

[English](README.en.md) | 简体中文

把模型端点公布的推理能力，同步进 DSH profile 的模型配置 —— 让模型选择器里的等级跟着端点走，
而不是靠手写 `cordis.patch.yml` 并且随端点漂移。

> **状态**：设计阶段。行为契约见仓库里的 spec issue，实现尚未开始。

## 它补的是哪一段

DSH 内置的「获取可用模型」把候选元数据削平到 `id` / `name` / `contextWindow` / `maxTokens` /
`inputModalities`：端点上公布的推理能力到不了配置里。而推理等级是**每个模型自己**的能力，
没有等级声明，选择器里就没有等级可选。

本插件**不接管**那条发现流程 —— 同一个 settings 命名空间只允许注册一份发现实现，外部插件
顶不进去 —— 而是**另开一条同步通道**：

- **Host 半边**读凭据、取端点目录、算出计划、写进配置；
- **Client 半边**注册进「设置 → 模型」页面为外部插件预留的座位，展示差异并触发同步；
- 同一个操作也作为 agent 工具暴露：**一个操作，两个调用者**，共用一份实现。

## 能做 / 不能做

能做：

- 在 provider 卡片里看到"端点公布的等级"与"当前声明"的差异
- 一键把差异写进配置，只改 `reasoningEfforts` 一个字段，不重建模型行
- 让等级跟着端点走：端点加了档位、撤了档位，重跑一次同步就对齐

不能做：

- **改不了「获取可用模型」按钮返回的候选内容。** 那几处字段白名单在 DSH 应用内部，
  只有上游修复才能让"发现即带上能力"成立
- 不新增、不删除模型：只同步**已声明**模型的能力
- 不写 `off` 键 —— 对 mandatory 模型那会 400
- 不猜端点没公布的能力：未知一律判保持原样

## 装进 profile

实现后补：作为 bundle 挂进 `~/.dsh/profiles/<profile>/` 的 `dsh.profile.bundles`。
